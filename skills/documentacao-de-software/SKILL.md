## 1. Overview and Governance

This skill acts as a unified software documentation specialist, ensuring all generated documentation is clear, traceable, testable, and free of ambiguities.

- **Restricted Scope:** The agent works only on documentation. Modifying the project's source code is strictly prohibited.
- **Context Reading:** Before starting any task, the agent must read the `README.md` and other guidance documents.
- **Version Governance:** Any change to any document must increment the version number (SemVer MAJOR.MINOR.PATCH) in the document and in the Change History Table. There are no silent exceptions.
- **Mandatory Authorship (Blocking Rule):** Every document created or modified must identify the real name of the responsible human author. The following rules apply:
  - The author field must be filled with a **real person's full name** (e.g., "João da Silva").
  - The following are **strictly prohibited** as author: "Copilot", "IA", "AI", "Agent", "Automatic", "System", "Anonymous", "N/A", "—" or any variation that does not identify a person.
  - If the author's name is not known at the time of creation or modification, the agent **must stop** the task and ask the user: _"What is the name of the author responsible for this document? The field cannot be filled with a generic or automated name."_
  - The agent may only proceed after receiving a valid human name.

## 2. Mandatory Bidirectional Traceability

Documentation cannot have loose ends. The agent must ensure:

- **Backward traceability:** Every requirement must have a clear origin (why it exists and who requested it), allowing impact assessment of changes.
- **Forward traceability:** Every requirement must point to derived technical artifacts (classes, tables, endpoints, test cases).

## 3. Ambiguity Handling and Defect Classification

Documentation cannot contain assumptions. The agent will act as a relentless reviewer.

- When ambiguities are found, the user must be questioned via handoff (skill `clarification`).
- **Document Defect Classification:** When reviewing or updating documentation, the agent must classify issues found as:
  - **Severity:** _Critical_ (prevents use/missing essential requirement), _Major_ (affects use but has workaround), _Minor_ (text/style errors).
  - **Nature:** _Omission_ (missing section/rule), _Violation_ (inconsistency with another document), _Imprecision_ (ambiguity), _Style_ (formatting).

- **Language Rule (BLOCKING):** ALL descriptive content of `req-XXXX` must be written in **Brazilian Portuguese (pt-BR)**, without any exception. The use of the following is **strictly prohibited**:

  - Library, framework, technology names (e.g., "React", "Node.js", "SQL Server", "Entity Framework", "Spring Boot", "Django", "Express", "Angular")

- **Automatic Correction (Blocking Rule):** When updating an existing `req-XXXX`, if the agent identifies Language Rule violations, these **must be automatically corrected** in the document before finalization. The agent must not question the user about these corrections — compliance with the language rule is non-negotiable. Examples of automatic correction:
  - "O **endpoint** /users retorna dados" → "A **rota** /users retorna dados" (if it cannot be avoided, translate and keep only if absolutely necessary for developer technical clarity in tec-req-XXXX)
  - "Implementar **cache** com TTL de 5 minutos" → "Implementar **armazenamento temporário** com validade de 5 minutos"
  - "O sistema usa **JWT** para autenticação" → "O sistema usa **tokens seguros** para autenticação" or "O sistema usa **credenciais criptografadas** para autenticação"
  - "A tabela `tb_usuario` contém os dados" → "A tabela de usuários contém os dados"
- **Non-Technical Audience (Fundamental Rule):** The `req-XXXX` is written **exclusively** for people without technical knowledge — clients, end users, managers, directors, business analysts. The agent must write as if the reader has **never used a similar system before**. This means:
  - Use complete sentences, never bare bullet points or IT jargon.
  - Prefer narrative paragraphs that explain the **why** and **how** before listing items.
  - Never assume the reader knows terms like "endpoint", "payload", "backend", "refactoring", "query", "trigger", or similar.
- **Clarity and Self-Sufficiency:** The `req-XXXX` must be **understandable on its own** by any stakeholder (client, PO, manager, user) **without needing developer or analyst assistance** to explain how it works.
- **Deliberate Verbosity:** Longer, detailed, and narrative descriptions are preferred over short descriptions. The document must answer, for each described feature:
  - What is it? (feature description in everyday language)
  - What is it for? (business value and user benefit)
  - Who uses it? (user profile that interacts with the feature)
  - When does it happen? (context and moment of use)
  - How does it work step by step? (narrated flow from the user's perspective)
  - What happens if it goes wrong? (expected behavior in case of error, in friendly language)
- **Richness of Details:** The document must describe the requirement with sufficient depth for all parties to understand what will be delivered, why it will be delivered, and how it will work in day-to-day use.
- **Mandatory Diagrams:** Every `req-XXXX` must **mandatorily** contain `mermaid` diagrams to illustrate the information flow. Rules:
  - **Minimum requirement:** at least one `flowchart` or `sequenceDiagram` illustrating the main end-to-end flow.
  - **Additional diagrams recommended:** for each alternative flow or relevant error case, include an additional diagram.
  - Diagrams must be positioned **immediately after** the narrative description of the flow they illustrate.
  - Use labels in Portuguese, with boxes and arrows that dispense with additional technical explanations.
  - **Syntax validation (Blocking Rule):** before finalizing the document, the agent must manually validate each Mermaid diagram against the most common errors that prevent rendering:
    - `flowchart` (written correctly, without variations like `flowChart` or `flow-chart`)
    - Every node with format `[text]` (rectangle), `{text}` (diamond), `(text)` (rounded) must have brackets/parentheses **correctly closed**
    - Arrows: `-->`, `==>`, `-.->` written without extra spaces
    - Edge labels in the pattern `-->|label|` or `-- label -->` without breaks
    - Labels with special characters (parentheses, brackets, colons, quotes) must use double quotes: `A["text with (parentheses)"]`
    - `sequenceDiagram` with declared participants and `->>` lines without extra spaces
    - `subgraph` / `end` blocks correctly paired
  - Minimum expected example (adaptable to context):
  ```mermaid
  flowchart TD
      A[User requests] --> B{System validates}
      B -->|OK| C[Processes request]
      B -->|Error| D[Returns friendly message to user]
      C --> E[Displays result to user]
  ```
- **Accessible Language:** Technical terms should be avoided or, when unavoidable, explained in a simple glossary within the document itself. No technical knowledge assumption may be made about the reader.
- **Concrete Examples:** The document must include practical usage examples (input → processing → output) to illustrate expected behavior. Examples with realistic fictional data (names, values, dates) make the document more understandable than abstract descriptions.

Only the technical description of how to implement it is prohibited in `req-XXXX`.
  - "Function Point Analysis (APF)"

## 7.1 Automatic Correction of Document Non-Conformances

**Blocking Rule:** When updating any document (especially `req-XXXX`, `tec-req-XXXX`, and master artifacts), if the agent identifies compliance violations (section 0 and non-negotiable rules of this skill), these **must be automatically corrected** without needing to question the user. Compliance is non-negotiable.

### 7.1.1 Scope of Automatic Correction

The following categories of non-conformance **must be automatically corrected** during any update:

1. **Language Violations (req-XXXX):**
   - English technical terms → translate or replace with Portuguese explanation
   - Code names (classes, methods, variables, tables) → rewrite in business language
   - Technical abbreviations without explanation → expand with Portuguese explanation
   - Technical jargon → translate to accessible language

2. **Format Violations (All artifacts):**
   - Missing mandatory fields (Author, Version, Date) → automatically add with appropriate value
   - Incomplete change history → update with new entry
   - Missing document references → add traceability section if absent

3. **Structural Violations (All artifacts):**
   - RF/BR numbering out of sequence → correct to maintain global continuity
   - Technical sections in `req-XXXX` that should be in `tec-req-XXXX` → automatically move
   - Mermaid diagrams with incorrect syntax → fix simple errors (brackets, arrows, subgraph/end)

4. **Traceability Inconsistencies:**
   - Requirement references a non-existent RF/BR in the master → ask if it is a new creation or numbering error
   - Document does not list its derived artifacts (estimate, criteria) → add references

5. **Wireframe/Mockup Violations:**
   - Missing PNG image at `documentacao/padrao_visual/wireframe/req-XXXX.png` → attempt generation via fallback; if still missing, record as blocking pending item
   - req-XXXX contains ASCII wireframe when PNG was possible → replace ASCII with PNG
   - tec-req-XXXX missing ASCII wireframe → add ASCII wireframe
   - tec-req-XXXX missing PNG reference → add PNG reference with path

### 7.1.2 Automatic Correction Process

When a non-conformance is detected:

1. **Classify** the non-conformance by type (language, format, structure, traceability).
2. **Correct** if it is simple and unambiguous (e.g., translate "backend" → "camada de processamento").
3. **Ask** only if there is ambiguity or a business decision is needed (e.g., what is the Portuguese name for the object "userData"?).
4. **Record** the correction in the change history with brief justification (e.g., "Automatic correction: translation of English terms to Portuguese per Language Rule").

| Non-Conformance                                                               | Expected Behavior                                                                                                |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Text: "O **endpoint** GET /users retorna uma **JSON response** com os dados." | Automatically correct to: "A **rota de consulta** GET /users retorna **dados estruturados** com as informações." |
| Text: "Tabela `tb_usuarios` com coluna `email_verified`"                      | Automatically correct to: "Tabela de usuários com coluna indicando se o e-mail foi verificado"                   |

### 7.1.4 Acceptance Criteria

- A document update is considered **non-compliant** if it is finalized without all obvious non-conformances (language, format, structure) having been automatically corrected.
- It is considered **acceptable** to question the user only when there is ambiguity or a decision needed; obvious automatic corrections are never submitted to a vote.

## 15. Functional Requirements (FR) and Business Rules (BR) Governance

### 15.1 Continuous Numbering Principle (Blocking Rule)

Functional Requirements (FR) and Business Rules (BR) numbering is **global and continuous** throughout the project, regardless of the `req-XXXX` document in which they are declared.

- **FR** follows the pattern `RF-XXXX` with 4 digits (e.g., `RF-0001`, `RF-0002`).
- **BR** follows the pattern `RN-XXXX` with 4 digits (e.g., `RN-0001`, `RN-0002`).
- Numbering **never restarts** for each requirement. Example:
  - `req-0001` may contain `RF-0001`, `RF-0002`, `RN-0001`.
  - `req-0002` must continue from `RF-0003`, `RN-0002`.
- Reusing the same FR or BR number in different documents is **prohibited**.

**Mandatory agent flow (Blocking Rule):**

1. Before creating any FR or BR in a `req-XXXX`, the agent **must** open and read the files `regras/requisitos-funcionais.md` and `regras/regras-negocios.md`.
2. Identify the "Next available number" field to know which number to use.
3. Insert the new FR or BR in the master document **before** referencing it in `req-XXXX`.
4. Update the "Next available number" field in the master to the following number.
5. **Never** assume that numbering starts at 0001 within a new `req-XXXX`.

> ⚠️ **Common error that must be avoided:** creating a `req-0002` with FR-0001 because the agent did not consult the master document. FR-0001 may already exist in `req-0001`. Numbering must continue from where it left off.

### 15.2 Master Documents (Single Source of Truth)

The files below are the **single source of truth** for FR and BR in the project. Each master file must contain a metadata header with `Version`, `Date`, and `Author` (real human name, per section 1), followed by a `## Change History` section, per the mandatory authorship and version governance rules of section 1.

| File                       | Location                                                                              | Content                                                      |
| -------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `requisitos-funcionais.md` | `documentacao/processo_unificado/artefatos_aprovados/detalhamento_requisitos/regras/` | All FRs in the project with continuous numbering, no repeats |
| `regras-negocios.md`       | `documentacao/processo_unificado/artefatos_aprovados/detalhamento_requisitos/regras/` | All BRs in the project with continuous numbering, no repeats |

Minimum structure of each entry in these documents:

```markdown
### RF-XXXX — [Short title]

**Source Requirement:** req-XXXX
**Description:** [Complete description of the functional requirement]

```


Every content update to an FR or BR **must** follow this flow:

1. Update the text in the master document (`requisitos-funcionais.md` or `regras-negocios.md`).

3. Record the change history in the master document.
4. Modifying an FR or BR directly in a `req-XXXX` or `tec-req-XXXX` without updating the master first is **prohibited**.

### 15.5 Creating New FRs and BRs

1. Before creating a new FR or BR, check the master documents to get the next available number.
2. Insert the new entry in the corresponding master document.
3. Reference the identifier in the associated `req-XXXX` and `tec-req-XXXX`.
4. Update the "Documents that use it" field in the master.

## 16. Complete Acceptance Criteria (`cri-req-XXXX`)

### 16.1 Blocking Rule

### 16.2 Purpose

The `cri-req-XXXX` must contain **all possible acceptance criteria** of the requirement, covering:

- Main flow (happy path).
- Alternative flows.
- Exception and error flows.
- Edge cases.
- Input/output validations.
- Permission/profile restrictions (when applicable).

The criteria must be written in **Gherkin** format (`Given / When / Then`) using `And` and `But` when necessary.

### 16.3 Generation Process (Mandatory)

Criteria generation must use an **exploratory model in conjunction with the `brainstorm` skill**:

1. Apply the `brainstorm.md` understanding protocol to map all actors, flows, and edge cases of the requirement.
2. For each identified combination (actor × action × result), generate a distinct Gherkin scenario.
3. Mandatory coverage: success, validation failure, permission failure, incorrect prior state, and concurrency (when applicable).
4. Review the generated set and eliminate only exact duplicates; never eliminate context or state variations.

### 16.4 Constraint in req-XXXX and tec-req-XXXX Documents

- The `req-XXXX` and `tec-req-XXXX` documents must contain **at most 5 acceptance criteria** (Gherkin), selected from the most representative and highest-risk ones in `cri-req-XXXX`.
- Selection of the 5 criteria should prioritize: main flow + cases with the highest negative impact if they fail.
- The `cri-req-XXXX` document is the complete source; the 5 criteria in the other documents are an executive summary.

### 16.5 Scenario Location, Naming, and Numbering

- **Location:** `documentacao/processo_unificado/artefatos_aprovados/detalhamento_requisitos/criterios/cri-req-XXXX-nome.md`
- **Naming:** `cri-req-XXXX-nome_do_requisito.md` (same suffix as the corresponding `req-XXXX`).
- **Scenario numbering (`CA-NNN`):** numbering is **local per document** — restarts at `CA-001` for each new `cri-req-XXXX`. Unlike FRs and BRs which are project-global, acceptance criteria are specific to each requirement.

#### 21.7.3 Pattern Selection Decision Tree

When the user needs guidance to choose between architectural patterns, the agent **must** use the following decision tree to recommend the most appropriate option:

```
START: What is the MAIN concern?

┌─ Data Access Complexity?
│  ├─ HIGH (complex queries, testing needed)
│  │  → Repository Pattern + Unit of Work
│  │  VALIDATE: Will data source change frequently?
│  │     ├─ YES → Repository worth the indirection
│  │     └─ NO  → Consider simpler ORM direct access
│  └─ LOW (simple CRUD, single database)
│     → ORM directly
│     Simpler = Better, Faster
│
├─ Business Rules Complexity?
│  ├─ HIGH (domain logic, rules vary by context)
│  │  → Domain-Driven Design
│  │  VALIDATE: Do you have domain experts on team?
│  │     ├─ YES → Full DDD (Aggregates, Value Objects)
│  │     └─ NO  → Partial DDD (rich entities, clear boundaries)
│  └─ LOW (mostly CRUD, simple validation)
│     → Transaction Script pattern
│     Simpler = Better, Faster
│
├─ Independent Scaling Needed?
│  ├─ YES (different components scale differently)
│  │  → Microservices WORTH the complexity
│  │  REQUIREMENTS (ALL must be true):
│  │    - Clear domain boundaries
│  │    - Team > 10 developers
│  │    - Different scaling needs per service
│  │  IF NOT ALL MET → Modular Monolith instead
│  └─ NO (everything scales together)
│     → Modular Monolith — Can extract services later when proven needed
│
└─ Real-time Requirements?
   ├─ HIGH (immediate updates, multi-user sync)
   │  → Event-Driven Architecture
   │  → Message Queue (RabbitMQ, Redis, Kafka)
   │  VALIDATE: Can you handle eventual consistency?
   │     ├─ YES → Event-driven valid
   │     └─ NO  → Synchronous with polling
   └─ LOW (eventual consistency acceptable)
      → Synchronous (REST/GraphQL)
      Simpler = Better, Faster
```

**The 3 Questions Before ANY Pattern:**

1. **Problem Solved:** What SPECIFIC problem does this pattern solve?
2. **Simpler Alternative:** Is there a simpler solution?
3. **Deferred Complexity:** Can we add this LATER when needed?

- Framework, library, or major dependency choice
- Data model or schema design
- Authentication strategy selection
- Architecture decision (REST vs GraphQL vs gRPC, monolith vs microservices)
- Build tools, hosting, or infrastructure choice
- Any decision that would be costly to reverse

### 21.9 Architecture Validation Checklist

> Incorporated from the `architecture` skill. Use this checklist before finalizing any architecture document or ADR.

Before considering an architecture document or ADR as complete:

- [ ] Requirements clearly understood and documented
- [ ] Constraints identified (scale, team, timeline, budget, domain)
- [ ] Each significant decision has a trade-off analysis documented
- [ ] Simpler alternatives were considered and explicitly rejected with rationale
- [ ] ADRs written for all significant architectural decisions
- [ ] Team expertise matches chosen patterns (or training plan exists)
- [ ] Pattern selection follows the decision tree (section 21.7.3)
- [ ] Anti-patterns avoided (premature microservices, over-abstraction, over-engineering)
- [ ] Architecture document references related ADRs
- [ ] The "Simplicity principle" was respected: complexity added only when proven necessary
